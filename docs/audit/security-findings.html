CRITICAL

Weak, committed JWT signing secret with silent prod fallback

SEC-01
Location
backend/src/main/resources/application.yml:42
Issue
The HS256 secret defaults to a known, source-committed string: ${JWT_SECRET:dev-only-secret-change-me-in-production-min-32-chars-please}. If JWT_SECRET is not set in production, the app boots anyway using this public value. Anyone who reads the repo can forge valid access tokens for any user/role.
Impact
Full authentication bypass and privilege escalation — an attacker can mint a token with role: OWNER/AGENCY/ADVERTISER and any uid.
Fix
Fail fast: require JWT_SECRET in the prod profile (no default), inject a high-entropy 256-bit random secret from a secrets manager, and never commit a real key. Consider rotating to asymmetric (RS256/EdDSA) so only the auth service holds the private key.

HIGH

JWTs (access + refresh) stored in localStorage

SEC-02
Location
frontend/src/lib/authStorage.js
Issue
Both tokens live in localStorage (ab_access_token, ab_refresh_token). Any XSS on the site — including via a third-party script or a future dangerouslySetInnerHTML data path — can read and exfiltrate them.
Impact
Full session theft; the long-lived (7-day) refresh token is the worst to lose.
Fix
Store the refresh token in an HttpOnly, Secure, SameSite cookie so JS can't read it; keep only the short-lived access token in memory. Add a strict Content-Security-Policy. If cookies are used, re-enable CSRF protection accordingly.
HIGH

No rate limiting or brute-force protection on auth endpoints

SEC-03
Location
AuthController /login, /register, /refresh
Issue
Login, registration, and refresh accept unlimited attempts. No lockout, throttling, CAPTCHA, or backoff.
Impact
Credential stuffing / password brute-forcing and registration spam are unimpeded.
Fix
Per-IP and per-account rate limiting (bucket4j, gateway, or Spring filter), exponential backoff, and account lockout after N failures. Add CAPTCHA on repeated failures.
HIGH

Hard-coded OTP (123456) — verification is a client-side sham

SEC-04
Location
frontend/src/features/register/widgets/otp.jsx:60,79
Issue
Email/phone "verification" passes whenever the user enters 123456, entirely in the browser. There is no server-side generation or check, so any registrant is trivially "verified".
Impact
Ownership of a phone/email is never actually proven — undermines trust, enables fake accounts and impersonation of contact details.
Fix
Move OTP to the backend: generate, hash+store, expire, rate-limit, and verify server-side; deliver via a real SMS/email provider (see Integration Gaps). Persist a verified flag the server enforces.

MEDIUM

Refresh tokens stored in plaintext

SEC-05
Location
RefreshTokenService.java:27 · RefreshToken entity
Issue
The opaque refresh token (a raw UUID) is persisted and looked up by its literal value. A read-only DB leak (backup, SQLi, log) yields directly usable tokens.
Fix
Store only a SHA-256 hash of the token; compare hashes on verify. Add reuse-detection: if a already-rotated token is presented, revoke the whole family (likely theft).
MEDIUM

Access tokens can't be revoked before expiry

SEC-06
Location
JwtService.java · JwtAuthenticationFilter.java
Issue
Access tokens are validated purely by signature + expiry. Logout only revokes the refresh token; a stolen access token stays valid for its full 15-minute window even after logout, password change, or role change.
Fix
Accept the 15-min window as the trade-off, or add a token version / jti denylist checked in the filter for high-value actions and on password/role change.
MEDIUM

Account/email enumeration on registration

SEC-07
Location
AuthService.register → EmailAlreadyExistsException
Issue
Registration returns a distinct "email already exists" error, letting an attacker enumerate which emails hold accounts. (Login correctly uses a generic message — good.)
Fix
Return a generic response and, where a verification email exists, send an "account already exists" notice out-of-band instead of revealing it inline.
MEDIUM

H2 console enabled with blank DB password (dev profile)

SEC-08
Location
application-dev.yml · SecurityConfig.java:37 (/h2-console/**)
Issue
The dev profile runs H2 with username: sa / empty password and exposes /h2-console/** as a public path with frameOptions: sameOrigin. Fine locally, dangerous if the dev profile is ever the active profile on a reachable host.
Fix
Ensure dev never runs in deployed environments; gate the H2 console + its permitAll behind the dev profile only (not the shared SecurityConfig).
MEDIUM

Production DB password defaults to empty

SEC-09
Location
application-prod.yml:7
Issue
password: ${DB_PASSWORD:} — if the env var is unset, the app connects (or tries to) with an empty password rather than failing.
Fix
Remove the default so a missing DB_PASSWORD fails fast; source it from a secrets manager.
MEDIUM

No JWT issuer/audience claims or validation

SEC-10
Location
JwtService.java:28-38, 57-63
Issue
Tokens set only subject/uid/role/exp; no iss/aud is issued or verified. Reduces defence-in-depth against token reuse across environments/services.
Fix
Set and verify issuer and audience; keep a small allowed clock skew explicit.

LOW

CSRF disabled globally

SEC-12
Location
SecurityConfig.java:62
Issue
Acceptable today because auth is bearer-token in a header (not cookies). Becomes a real CSRF hole the moment any cookie-based auth is introduced (see SEC-02's cookie recommendation).
Fix
If you move refresh tokens to cookies, re-enable CSRF protection (e.g. double-submit token) for state-changing requests.
LOW

Permissive CORS headers with credentials

SEC-13
Location
SecurityConfig.java:75-84
Issue
allowCredentials(true) with allowedHeaders("*"), and a single hard-coded origin. Origin is fine, but the wildcard headers are broader than needed and the allow-list isn't env-driven for prod.
Fix
Enumerate the headers actually required; drive allowed origins from configuration per environment.
LOW

Trusted-HTML rendering pattern (future risk)

SEC-14
Location
Browse/browseData.js ICON_SVG → dangerouslySetInnerHTML
Issue
Icons render via dangerouslySetInnerHTML. Safe now (static, developer-authored), but if this rendering path is ever fed backend/user data it becomes stored XSS — which would also compromise the localStorage tokens (SEC-02).
Fix
Keep these paths strictly static, or render as React SVG components; sanitize if any dynamic HTML is ever introduced.
