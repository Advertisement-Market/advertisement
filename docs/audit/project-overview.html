The frontend is a decoupled single-page app: it never renders on the server or talks to the database directly. Every interaction goes through the REST API over JSON, with the JWT attached as an Authorization: Bearer header. The two run as independent processes (Vite on :5173, Spring Boot on :8080), connected via a configured CORS allow-list.

Authentication — JWT, in depth

Auth is stateless and token-based. There are no server-side HTTP sessions; instead the server issues signed tokens the client presents on each request. Two token types work together — a short-lived access token and a longer-lived, revocable refresh token.

What happens on a request:

Register or log in

Client POSTs to /api/auth/login or /api/auth/register/{role}. The server verifies the BCrypt-hashed password (via Spring Security's AuthenticationManager) and, on success, issues an access + refresh token pair.

Store the session

The frontend saves both tokens and the user object in localStorage (authStorage.js) so the session survives reloads.

Call a protected endpoint

An Axios request interceptor attaches Authorization: Bearer <accessToken> to every call automatically.

Server validates the token

JwtAuthenticationFilter parses and signature-checks the JWT, loads the user, and populates the Spring Security context. Public paths (auth, ping, health) skip this; everything else requires a valid token.

Access token expires → silent refresh

On a 401, a response interceptor calls /api/auth/refresh once with the refresh token, gets a fresh pair, and replays the original request — transparent to the user.

Rotation & logout

Each refresh revokes the presented token and issues a new one (single-use rotation). Logout revokes the refresh token server-side and clears localStorage.

Why two tokens? The access token is fast to verify (no DB lookup) but can't be revoked before it expires — so it's kept short (15 min). The refresh token lives in the database, so it can be revoked and rotated, letting sessions last days without keeping a long-lived, un-revocable credential in play. Roles (ADVERTISER / OWNER / AGENCY) are embedded in the token and drive both backend authorization and which dashboard the frontend routes to.
