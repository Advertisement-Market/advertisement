## 1. Overview & Business Requirements

- **Goal:** Implement a centralized, backend-driven notifications platform powering the Topbar and Dashboard Overview capsules across all platform personas (`OWNER`, `ADVERTISER`, `AGENCY`, `MEMBER`), replacing hardcoded client-side mock data.
- **User Impact:** All dashboard users (starting with Billboard Owners) receive real-time, persistent notification feeds for inbound quote requests, listing views, tender matches, payment receipts, and onboarding progress with persistent read tracking.
- **Key Architectural Decisions:**
  - **Shared Data Model (`notifications` table):** Keyed directly on `user_id` rather than persona-specific tables, preventing table duplication and following the normalization standards established in PR-11.
  - **Strict Naming Standardization (`created_ts`):** Adheres to the `_ts` suffix convention established in `V3__normalize_schema.sql`.
  - **Type-Safe Enums:** `NotificationCategory` and `NotificationTone` enums prevent silent typing bugs while serializing cleanly to frontend CSS class tokens (lowercase tone strings).
  - **Safe, Idempotent `GET` Lifecycle:** Starter welcome notifications are created deterministically during registration (`OwnerRegistrationService.register()`), eliminating race conditions and side effects on `GET /api/notifications`.
  - **Row-Level Security & Isolation:** Mutations (`PATCH /api/notifications/{id}/read` and `POST /api/notifications/read-all`) are scoped strictly to the authenticated `user_id`. Attempting to read another user's notification returns `404 Not Found` (indistinguishable from nonexistent IDs to prevent enumeration).
  - **Bounded Querying:** Capped at 50 most recent items (`findTop50ByUserIdOrderByCreatedTsDesc`) to guarantee high-performance retrieval and bounded memory.

## 3. Database Schema & Migration (`V4__create_notifications.sql`)

```sql
CREATE TABLE notifications (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id     BIGINT       NOT NULL,
    title       VARCHAR(150) NOT NULL,
    message     VARCHAR(500) NOT NULL,
    category    VARCHAR(50)  NOT NULL,
    tone        VARCHAR(20)  NOT NULL,
    target_url  VARCHAR(255),
    is_read     BOOLEAN      NOT NULL DEFAULT FALSE,
    created_ts  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_notifications_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
);

CREATE INDEX idx_notifications_user_created ON notifications(user_id, created_ts DESC);
CREATE INDEX idx_notifications_user_read ON notifications(user_id, is_read);
```

## 4. API Specification & Contracts

### 1. `GET /api/notifications`
- **Description:** Returns the 50 most recent notifications for the authenticated user and total unread count.
- **Authentication:** Bearer JWT required (`MEMBER`, `ADVERTISER`, `OWNER`, `AGENCY`).
- **Response `200 OK`:**
  ```json
  {
    "unreadCount": 1,
    "notifications": [
      {
        "id": 101,
        "title": "Welcome to The AdBasket!",
        "message": "Your account is registered. Your listing \"BKC LED Screen\" is under review and will be active shortly.",
        "category": "ONBOARDING",
        "tone": "teal",
        "targetUrl": "/owners/dashboard",
        "read": false,
        "createdAt": "2026-09-13T22:00:00Z"
      }
    ]
  }
  ```

### 2. `PATCH /api/notifications/{id}/read`
- **Description:** Marks a single notification as read.
- **Authentication:** Bearer JWT required.
- **Response `204 No Content`:** Success.
- **Response `404 Not Found`:** If notification ID does not exist or does not belong to the caller.

### 3. `POST /api/notifications/read-all`
- **Description:** Marks all unread notifications for the caller as read.
- **Authentication:** Bearer JWT required.
- **Response `204 No Content`:** Success.
